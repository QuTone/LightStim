# Logical Compiler to Rotated-Surface PPM

This example maps a placed logical PPM program to LightStim without adding a
compiler IR inside LightStim:

```text
placed logical program
    -> RotatedSurfacePatchPlacement + RotatedSurfacePPMStep
    -> RotatedSurfacePPMExperiment.build()
    -> Stim circuit, DEM, lowering certificate, PPM result records
```

The JSON is an illustrative caller-owned format. A real compiler should map
its native IR directly in the same small adapter.

## Minimal Input

[`sequential_ppm.json`](sequential_ppm.json) contains only patch placement and
a complete logical operation sequence:

```json
{
  "patches": {
    "A": {"cell": [0, 0], "orientation": "X_horizontal"},
    "B": {"cell": [2, 0], "orientation": "X_horizontal"}
  },
  "operations": [
    {"prepare": {"A": "Z", "B": "Z"}},
    {"ppm": [["A", "Z"], ["B", "Z"]], "route": [[1, 0]]},
    {"measure": {"A": "Z", "B": "Z"}}
  ]
}
```

### Declared vs Generated

| value | why |
|---|---|
| patch cell and orientation | required physical mapping input; LightStim is not the placer |
| optional patch `stabilizer_frame` | physical patch convention: `standard` (default) or `conjugate` |
| `prepare` and `measure` operations | logical program semantics; they cannot be inferred from a PPM target |
| PPM target pairs | the logical operation being lowered |
| explicit route | required backend input; this implementation has no auto-router |
| distance, rounds, physical error rate | execution arguments, not logical-program fields |
| physical origin, checks, schedule, detectors, records, DEM | generated by the adapter and LightStim |

The adapter maps the explicit `conjugate` stabilizer frame to LightStim's
lower-level ``colour_swapped`` construction. The backend boolean is not exposed
in the program format. A conjugate frame swaps the patch's X/Z stabilizer
labels without changing its physical footprint; this is required by some
executable mixed-Pauli joins.

Operations and lowering results correspond by list position. A caller with
stable source-operation handles should retain its own source map rather than
injecting presentation IDs into this format.

Preparation/readout bases matter even when they look obvious in this example.
The same PPM can be deterministic or intentionally random depending on the
incoming logical state, and the final basis depends on the rest of the logical
program. They therefore belong in `operations`, not in patch metadata and not
inferred from the PPM itself.

## Included Programs

- [`sequential_ppm.json`](sequential_ppm.json): three collinear patches and two sequential
  commuting two-body PPMs.
- [`weight3_ppm.json`](weight3_ppm.json): one T-shaped, true
  three-body `M(Zq1 Zq2 Zq3)` measurement.
- [`checkerboard_3x3_ppm.json`](checkerboard_3x3_ppm.json): nine patches and
  three distant PPMs covering `ZZ`, `XX`, and mixed `XZX` products.

They use the same format and adapter. Only the layout and operation sequence
differ.

[`visualization.ipynb`](visualization.ipynb) compiles all three programs and
uses Stim detector-slice diagrams to show complete syndrome-extraction
windows. It also demonstrates the explicit rejection of a Y factor at the
current backend boundary.

## Larger Validation Program

[`checkerboard_3x3_ppm.json`](checkerboard_3x3_ppm.json) places nine logical
patches on a 3x3 routing grid and executes three commuting,
non-overlapping distant PPM routes with weights 2, 2, and 3. They cover a pure
Z product, a pure X product, and an executable mixed `XZX` product using one
conjugate-frame patch. The benchmark compiles with `rounds=1` for compact
physical-circuit inspection.

Each neighbouring patch position is separated by one full coarse routing cell.
This is a routing-channel layout, not a compact packing: the current backend's
coarse cell has pitch `2d+2`, and the reserved corridor is deliberately wide
enough to host a distance-d merged region.

## Run

From the repository root:

```bash
python -m pip install -e .
python -m examples.integrations.logical_compiler_rotated_surface_ppm
```

Weight-3 example:

```bash
python -m examples.integrations.logical_compiler_rotated_surface_ppm \
  --program examples/integrations/logical_compiler_rotated_surface_ppm/weight3_ppm.json \
  --output-dir build/examples/logical_compiler_rotated_surface_ppm_weight3
```

`distance`, `rounds`, and one uniform circuit-level physical error rate are CLI
options:

```bash
python -m examples.integrations.logical_compiler_rotated_surface_ppm \
  --distance 5 --rounds 5 --physical-error-rate 0.001
```

## Code Boundary

[`adapter.py`](adapter.py) contains only parsing and the public LightStim
mapping, and returns an ideal circuit. [`__main__.py`](__main__.py) owns
optional noise injection, DEM/manifest generation, and CLI presentation. The
core translation is:

```python
placements = [RotatedSurfacePatchPlacement(...), ...]
steps = [RotatedSurfacePPMStep(targets=..., route=...), ...]
experiment = RotatedSurfacePPMExperiment(
    placements,
    steps,
    initial_states=states_from_prepare,
    final_measure_states=states_from_measure,
    rounds=rounds,
    colour_swapped=conjugate_frame_patch_names,
)
circuit = experiment.build()
```

Generated artifacts are written under `build/examples/`:

- `circuit_ideal.stim`: circuit before noise injection;
- `circuit.stim`: noisy evaluation circuit;
- `circuit.dem`: raw detector error model;
- `manifest.json`: ordered lowering summaries, exact-product status, and
  absolute Stim measurement indices for each PPM result. Detailed
  certificate items remain available through `result.experiment.plans` rather
  than being duplicated into the file.

An empty result-record list is fixed zero parity. `null` means the result was
not record-deterministic at that point, not that compilation failed.

## Current Boundary

Supported: standard/conjugate-frame rotated patches, explicit X/Z routes,
commuting sequences, and the verified weight-2/representative weight-3
geometries. Repeating the same commuting PPM on the same corridor is covered
by the core protocol tests; this larger example keeps distinct routes and does
not claim support for arbitrary partial overlap between different products.
The backend explicitly rejects Y factors, wall execution, anti-commuting
sequences, deformed patches, and unsupported route/weight combinations.

## Integration Decisions Left to the Caller

This example deliberately does not hide unresolved compiler policy behind the
adapter. An integrating compiler or router should decide:

- **routing ownership:** provide an explicit connected route today, or add an
  upstream router that emits and validates the same coarse-cell path;
- **Y-containing products:** synthesize them into supported X/Z measurements
  with the required ancilla-state operations and account for that overhead, or
  extend the physical backend with a validated native twist/Y-wall
  construction;
- **scheduling and liveness:** submit only supported commuting sequences, or
  add patch-liveness, feed-forward, and conflict-aware scheduling before using
  broader logical programs;
- **source mapping:** retain compiler-native operation handles outside this
  minimal schema and correlate them with results by sequence position.

For an initial integration, treat `certificate.measures_exactly_the_product`,
a noiseless detector/observable sample, and successful DEM construction as
handoff checks. They validate the implemented lowering path; they do not turn
unsupported geometries into supported ones.
